# ADR-005: libSQL/Turso as system of record, zod-beside-table validation, serialized columns

**Status:** Accepted. The nullable tenancy column is a standing candidate for supersession (NOT NULL migration); revisit the engine choice only with write-contention evidence.

## Context

The OLTP plane (ADR-004) is read-mostly, tenant-scoped, and modest in volume. The dashboard's tRPC runs on Next.js Edge, which rewards a database reachable over HTTP with replicas near users. The team optimizes for shipping speed; SQLite's type system is famously loose, and the ORM (Drizzle) is schema-in-TypeScript.

## Decision

libSQL (Turso) over HTTP as the system of record, accessed via `drizzle-orm/libsql/http`. Three schema-style conventions ride along: (1) **zod-beside-table** — every entity directory pairs `table.ts` with a `validation.ts` zod schema, and DB reads are `parse`d back into rich types; (2) **cheap serialization** — `regions` as comma-joined text, `assertions`/`headers` as JSON-in-text, validated by the zod layer rather than the database; (3) **timestamps as unix-seconds integers** with SQLite `strftime` defaults. Migrations are forward-only files generated by drizzle-kit; "rollback" is a new forward migration. Deploy discipline: additive-nullable first, backfill, then tighten — because four independently-deployed apps share the database.

## Evidence

- `packages/db/src/db.ts:6-12` — the HTTP driver client.
- `packages/db/src/schema/monitors/monitor.ts:13-73` — serialized columns (L26, L34, L45), `strftime` timestamp defaults (L59-64), the partial index `WHERE deleted_at IS NULL` on workspaceId (L68-72) matching the dominant query, and the wart: **nullable `workspaceId`** (L37).
- `packages/services/src/monitor/internal.ts:28-84` — the compensating machinery for nullable tenancy: fetch-or-throw helpers and ownership-validated join-table ids.
- `.github/workflows/test.yml:51-57` — CI applies migrations before tests; `packages/db/src/seed.mts` carries fixture state.

## Alternatives considered

1. **Postgres.** The default answer, rejected: heavier to operate, no edge-replica story at the time, and the workload shape doesn't need its concurrency model. Standing caveat: SQLite's limited `ALTER TABLE` turns many migrations into table rebuilds, and transaction isolation over the *HTTP* driver has never been fully characterized — nothing should depend on serializable semantics without verification.
2. **Normalized purity** (regions join table, JSON columns with constraints, NOT NULL + FK tenancy from day one). Rejected for speed; the zod layer compensates on read. Verdict in hindsight: right for the serialized columns, **wrong for nullable `workspaceId`** — tenancy enforced by every query remembering a filter instead of by the schema is discipline where structure was available.
3. **Validation in the DB** (CHECK constraints, triggers). Rejected: SQLite's toolkit is weak and the invariants need application context anyway (ADR-002).

## Consequences

**Positive:** near-zero operational cost; edge replicas pair with Edge tRPC; schema-in-TS keeps table, types, and validation in one directory — the zod-beside-table convention means a drifted read fails loudly at parse time instead of quietly corrupting downstream.

**Negative:** the zod sibling must ship in the same PR as any schema change or working migrations become runtime 500s; unix-seconds vs JS-milliseconds is a live foot-gun (`getScheduledTime` at `apps/workflows/src/cron/monitor.ts:393-407` mixes conventions); table-rebuild migrations raise the cost of tightening constraints, which quietly discourages ever doing it — one reason the NOT NULL tenancy migration has stayed hypothetical; and soft-delete via `deletedAt` interacts with `active` to produce 8 combined lifecycle states, not all of which every query handles (check whether `apps/workflows/src/cron/checker.ts:98-108` filters `deletedAt` — an unresolved bug-suspicion).
